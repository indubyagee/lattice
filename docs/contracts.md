# Supported implementation contracts

## Authority and boundaries

The Electron main process owns a project session and serializes semantic transactions. The renderer is sandboxed, context-isolated, and has no Node integration. The preload exposes named methods only; main-frame sender and origin checks protect IPC. Files are addressed by a named root and relative path; lexical and real-path checks reject traversal and junction/symlink escapes.

The domain, projection, validation, artifact-comparison, export-generation, and provider-contract modules have no Electron or React dependency. ESLint enforces these import boundaries. The validation engine uses a worker in the app and the host for explicit command previews; it is not evaluated inside the renderer's strict content security policy.

All semantic transactions carry a base revision. A batch advances the revision once, or leaves the snapshot unchanged. Stale proposals require recomputation. Unknown entity/relationship definitions preserve their records and produce unknown checks. Saving an editable draft is independent of specification readiness.

## Presentation and user preferences

View files can contain optional `containers` with separate IDs, name, description, position, dimensions and an optional `parentAppearanceId`. Appearances use the same parent field for frames or legacy appearance groups. Validation rejects missing/cyclic parents, identity collisions and invalid bounds. Reparenting and frame removal preserve world positions. Collapsing hides visual descendants; arrangement preserves relative child positions. All of these use view history and leave the semantic revision unchanged.

Graph cues derive from pinned relationship meaning and declared `properties.importance` (`low`, `normal`, `high`, `critical`). Importance affects width/labels, independently of deterministic finding severity. Directed definitions get target arrows; Contains adds an ownership diamond, Denies a stop bar, and undirected definitions omit arrows. Text labels, patterns, semantic icons and adjacency outlines complement color.

The typed preload exposes read/write appearance preferences and installed font enumeration. Preferences contain theme, interface/editor family and font size; the host validates bounds and changed font families against the Windows list, serializes writes and stores `appearance.json` in application-local user data. Font listing runs a fixed, hidden Windows command with no user-supplied command text. No font is downloaded. Appearance preferences are excluded from canonical data and exports.

0.3.0 extends preferences with independent `colors.light` / `colors.dark`, booleans `snapToGrid` / `snapToObjects`, `gridSize` (8–100 canvas units), `snapDistance` (2–24 screen pixels), `tooltipDelay` (0–3,000 ms) and `tooltipFontSize` (10–24 px). Colors must be six-digit hex strings; unsupported CSS/URLs cannot be injected. Missing new fields receive defaults when reading older font-only settings. UI preview/Cancel stay local until Apply. Resetting a mode restores its colors, including tooltip colors; Restore defaults resets the entire draft.

0.3.1 adds local booleans `showSystemConnections` and `graphTooltips`, both defaulting to false, including when absent from older preferences. The canvas toolbar persists both through the existing validated preferences IPC; Settings → Tooltips also controls `graphTooltips`. System connections are filtered at either System endpoint when building the canvas scene, including adjacency cues. Node visibility and semantic relationships remain unchanged. The tooltip preference covers hover and keyboard focus within the graph surface; help outside the graph stays available. Neither setting changes project revisions, layout history or exports.

Snapping computes a rigid selection bounding box in world space, excludes moving ancestry/descendants, matches edge/center anchors within tolerance divided by zoom, then falls back to grid on unmatched axes. Results are stored as parent-relative positions via existing layout mutations. Custom snapping handles multi-selection to preserve spacing. Keyboard grid steps bypass object attraction. Guides are decorative SVG in the viewport; node measurements and cached references remain intact. No semantic commands, relations or revisions are created by snapping or preference changes.

Original PNG/SVG branding is retained under `public/icons/icon-on-light*` and `public/icons/icon-on-dark*`. PNGs are bundled locally for renderer and native window icons. Windows packaging converts the dark asset for the executable, edits resources with code signing disabled, and bundles both original PNGs for runtime theme switching. No downloaded or regenerated artwork is used.

## JSON Schema and graph rules

Use Draft 2020-12 through Ajv's dedicated class. Coercion, default insertion, and removal of additional data are disabled. The supported keywords are:

`$schema`, `$id`, `$defs`, `$ref`, `type`, `title`, `description`, `default`, `properties`, `required`, `additionalProperties`, `items`, `enum`, `const`, `minimum`, `maximum`, `minLength`, `maxLength`, `minItems`, `maxItems`, `allOf`, `anyOf`, `oneOf`.

References are local fragments or `lattice:` references to definitions in the project package. Unsupported keywords fail registration. Defaults assist insertion; missing required properties become findings.

| Rule             | Declared behavior                                                                                                                                                                                     |
| ---------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `required`       | Require a property or JSON Pointer in properties.                                                                                                                                                     |
| `allowed`        | Compare a property with explicit JSON values.                                                                                                                                                         |
| `endpoint-port`  | Check endpoint families and exact port contract references; unresolved contracts are unknown.                                                                                                         |
| `relation-count` | Count the named exact relationship reference in the declared direction, with optional min/max.                                                                                                        |
| `dependency`     | Require an outgoing named relationship, optionally to an exact target type.                                                                                                                           |
| `access`         | Analyze intended tool use against explicit grants/denials. Absence is unspecified. Inheritance requires an explicit declaration.                                                                      |
| `reachability`   | Follow named outgoing relationships to an exact target type, with cycle detection and a 1–10,000 edge depth bound. A declared positive numeric loop bound can satisfy a configured bound alternative. |

These checks describe the specification; they do not enforce target-runtime permissions or establish termination. Impact analysis follows declared dependency directions, includes explanatory paths, defaults to three edges, and supports the full affected set.

Property rules apply to the properties of their own entity or relationship. Count, dependency, and reachability rules belong on entity types; endpoint and access rules belong on relationship types. Registration rejects unsupported placements. Scoped access inheritance currently follows an explicitly declared direct `contains` relationship with `inherit: true`; deeper scopes need their own explicit rules. It does not infer access from visual grouping or `systemIds`.

## Artifacts and reuse

Each binding declares independent, generated, or managed ownership. Mapping formats are `markdown` (bounded markers), `json` (JSON Pointer), and `text` (whole text). Baselines record accepted values, resource hashes, mapping version, and revision. Initial associations are labelled initial review rather than a three-way merge.

Assembly instances retain the pinned definition hash, definition-to-instance identities, parameters, and relationship mapping. Upgrades compare old definition, new definition, and local instance. Definition-only changes can apply; local overrides remain; conflicts need explicit dispositions. Imported packages verify content hashes and bundled dependencies.

## Exports and reviews

`portable-spec@1.0.0` generates a portable semantic specification. `codex-workspace@1.0.0` adds declared instructions at their relative directory scope and complete `.agents/skills/<slug>/SKILL.md` folders with declared text resources. Rendering nodes and layout never become canonical semantics.

Generation takes a frozen semantic revision and an injected timestamp. File order and content are deterministic for fixed inputs. The manifest hashes every other generated file and explicitly excludes its own recursive hash. Traceability maps model identities to generated sections and artifact references. Existing destination changes are reviewed before hash-checked writes.

`implementation-ready@1.0.0` requires mandatory checks to pass and current design reviews for responsibilities, interfaces, information, failure paths, and acceptance. Acknowledgement or severity does not convert a failed/unknown check into a pass. Review records cover a design hash that excludes review/disposition bookkeeping and content-preserving resource relocation.

## Provider boundary

Live provider selection and credential setup are deferred. The deterministic simulation only receives selected entities, their relevant definitions, and explicitly included excerpts. It emits reasoned command groups and assumptions. No provider can apply its own changes or record human approval, deterministic check dispositions, or implemented/verified claims. Accepted commands pass through the same revision-aware service.

Selecting an associated Markdown resource adds its exact loaded text and hash to the scope. Simulated file patches have a separate diff and Save action. Their original hash must still match; saving a patch does not accept any affected artifact mappings.

## Component and relationship schema reference

This reference describes the current `0.3.1` application and `1.0.0` project format. **Current** means represented or evaluated by this checkout. **Recommended** means a proposed contract, not an implemented field, validator, migration, or runtime feature. Descriptive meanings below interpret the existing catalog and help text; they do not add enforcement.

There are **38 component types, six component families, 28 relationship types, and eight derived edge categories**. A component type is a reusable definition; a component is an `Entity` instance. A relationship type is a reusable definition; an edge is a `Relationship` instance. Families classify component definitions. Categories currently classify edge presentation and are not semantic definition records.

### 1. Shared identity, defaults and validation contracts

| Concern               | Current contract                                                                                                                                                                                                                                                                     |
| --------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Definition identity   | `id` plus numeric `major.minor.patch` version; references use `id@version`. Built-ins use `lattice.<slug>@1.0.0`. Registration uses ID pattern `^[a-zA-Z][\w.-]+$`; a namespace separator is conventional, not required by that pattern. Prerelease/build suffixes are not accepted. |
| Pinning               | A registered exact version is immutable through registration commands. An identical re-registration is accepted; changed content requires a new version. Entity migration explicitly changes `typeRef` and retains properties.                                                       |
| Instance identity     | Factories generate UUIDs; envelope checks accept other nonempty stable string IDs. Project, entity, relationship, assembly-instance and binding IDs cannot collide. Definition map keys must equal `id@version`.                                                                     |
| JSON values           | `null`, boolean, number, string, array, or string-keyed object. `properties` must be an object. No functions, executable handlers, UI objects, or machine-specific paths belong in portable records.                                                                                 |
| Property schema       | Definition `schema` validates the instance's `properties`, not the entire entity/edge envelope. TypeScript interfaces and explicit envelope checks cover the outer record; runtime envelope checks do not exhaustively validate every nested interface field.                        |
| JSON Schema dialect   | Draft 2020-12, restricted to the keyword allowlist above. Local fragment and `lattice:` package references only. No remote retrieval, coercion, automatic validator defaults, or removal of extra data.                                                                              |
| Definition failure    | Malformed envelopes, unsupported rules/keywords and immutable-version changes are rejected. The host also compiles definition schemas.                                                                                                                                               |
| Specification failure | Missing required values, incompatible known endpoints and other semantic defects generally produce Findings while preserving an editable draft. A structurally missing relationship endpoint is rejected by project integrity checks.                                                |
| Unknown definitions   | Records survive; validation reports `unknown`. This is distinct from a compatible known definition.                                                                                                                                                                                  |
| Transactions          | `CommandBatch` supplies `baseRevision`, nonempty `operations` (maximum 5,000), `reason`, and optional `expectedDesignHash`. Success advances semantic revision once; stale or invalid batches leave the input unchanged.                                                             |
| Default semantics     | Defaults are insertion suggestions, not evidence or automatic valid values. Required text should remain missing until supplied; do not fill it with a placeholder that falsely passes readiness.                                                                                     |

**Current creation paths differ:** `createEntity()` starts with empty properties. Clicking the toolbox inserts only immediate `schema.properties.<key>.default` values. It does not recursively expand nested defaults or set corresponding value-status entries. Canvas drop calls `createEntity()` without copying schema defaults. Relationship creation starts with `{}` regardless of schema defaults. Assembly parameters separately use the supplied value or `parameter.default` through nullish fallback; an explicit `null` therefore falls back too. None of the built-in property schemas currently declares a `default`.

**Recommended:** centralize creation/default materialization in the portable domain layer, clone default objects, define the difference between missing and explicit `null`, and apply the same policy through click, drop, commands and proposals. Preserve the distinction between an inserted default and a reviewed declaration.

### 4. Ports and contracts

| `Port` field  | Type                  | Current default | Current validation                                                                                  |
| ------------- | --------------------- | --------------- | --------------------------------------------------------------------------------------------------- |
| `id`          | string                | None            | Nonempty and unique within its type definition. Stable local interface key, not a global entity ID. |
| `direction`   | `in` / `out` / `both` | None            | Must be one of those values.                                                                        |
| `contractRef` | optional string       | Absent          | Registration checks string shape only; does not require an exact version or resolve a contract.     |

Relationships optionally store `sourcePort` and `targetPort` IDs. If neither is supplied, no port check runs. If either is supplied, the engine looks up both ports on the endpoint definitions. Missing ports or missing contract refs produce `unknown`. With two refs present it checks **literal ref equality**, source direction other than `in`, and target direction other than `out`. Unequal refs or incompatible directions fail.

Consequently, two identical nonexistent contract refs can currently pass. There is no structural subtyping, conversion, payload validation, per-port connection count, required-port check or special bidirectional-port algorithm for undirected relationships. Endpoint and port checks are performed by the engine even when a custom relation omits the `endpoint-port` rule marker. Built-ins all include that marker.

The canvas renders one generic target handle on the left and one generic source handle on the right. Named semantic ports are selected in the connection form or Inspector. Edges are not currently routed to individual named handles, and the scene does not pass stored port IDs through as render handle IDs.

**Recommended port extension:** retain existing fields, then add `name` (default to ID), `description` (empty), `channel: data / control / context / artifact / access` (explicit), `required` (false), and optional `minConnections` / `maxConnections` (nonnegative integers with minimum no greater than maximum). Store side/order/label/visibility as presentation configuration, not access or data semantics. Require resolvable exact refs for typed ports; keep intentionally untyped interfaces explicitly distinguishable from unresolved contracts. Semantic associations may remain portless. For an undirected typed connection, require `both` ports until a richer policy is defined.

**Recommended contract registry:** add separately versioned `ContractDefinition` records with `id`, `version`, `name`, `description`, `schema`, and optional `mediaType`. `schema` describes the exchanged payload. A `context-contract` or `artifact-contract` entity can refer to one of these definitions. This avoids confusing a component's configuration-property schema with a message schema. No such registry is implemented today; current `lattice:` JSON Schema refs resolve component/relationship property schemas in the project.

### 7. Rule vocabulary and evaluation

| Kind             | Placement                            | Parameters and defaults                                                                             | Current meaning / limits                                                                                                                                                                                                           |
| ---------------- | ------------------------------------ | --------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `required`       | Component or relationship definition | `property: string`, required                                                                        | Value exists at the property key or supplied JSON Pointer. A present `null` counts as present; use a property schema to require a non-null/nonempty value.                                                                         |
| `allowed`        | Component or relationship definition | `property`, `values: JsonValue[]`, required                                                         | Compares canonical JSON hashes. Missing value is currently treated as `null` for comparison; use an independent required check when absence must fail.                                                                             |
| `endpoint-port`  | Relationship definition              | No parameters                                                                                       | Declarative marker; engine always checks known endpoint families and selected ports as described above.                                                                                                                            |
| `relation-count` | Component definition                 | Exact `relation`, `direction: in/out`; optional `min`, `max`; effective missing bounds 0/unbounded  | Counts matching relationship records. Bounds must be nonnegative integers; registration does not currently enforce `min <= max`. Undirected storage is not counted symmetrically.                                                  |
| `dependency`     | Component definition                 | Exact `relation`; optional exact `targetType`                                                       | Requires an outgoing edge of that exact reference, optionally to an entity with that exact type ref.                                                                                                                               |
| `access`         | Relationship definition              | No parameters                                                                                       | Intended use permission analysis for action `use`. Denial → fail; explicit grant → pass; neither → unknown. Not a general action authorization framework.                                                                          |
| `reachability`   | Component definition                 | `relations: string[]`, `targetType: string`, `maxDepth: integer` 1–10,000; optional `boundProperty` | Follows named outgoing edges with cycle protection. Positive numeric top-level bound property bypasses traversal. Existing rule accepts positive fractions too; it does not require integer iteration bounds or prove termination. |

Access analysis accepts matching `grants` / `denies` edges from the actor to the resource. A scope grant/denial applies to an actor only when that edge declares `inherit: true` and the scope directly `contains` the actor. It also accepts `access-rule` entities with matching `actorId`, `resourceId`, `action: 'use'`, and effect. The entity's own `inherit` field is not used by that second path. Other actions and deeper inheritance are not evaluated. Visual nesting and `systemIds` are never access grants.

There is no current general-purpose condition evaluator, acyclic-containment rule, uniqueness rule, exact endpoint type rule, port cardinality rule, schema-subtyping rule, or rule-specific severity override. A `validation-rule` component does not itself add any such capability. Checks are specification analysis, not target-system execution.

### 8. Additional records that need schema documentation

#### Views, appearances and visual containers

| Record           | Fields / defaults                                                                                                                                     | Contract                                                                                                                                         |
| ---------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| `Appearance`     | Required `id`, `entityId`, finite `x`, `y`; optional `hidden`, `parentAppearanceId`                                                                   | View identity distinct from entity ID. Missing hidden means visible. Position is relative to a parent when present; no parent means world space. |
| `ViewDefinition` | `id`: architecture/behavior/information/validation; `appearances: []`; optional `containers`; `collapsedIds: []`; `viewport: { x: 0, y: 0, zoom: 1 }` | Separate view history. View changes do not advance semantic revision. Zoom must be finite and positive.                                          |
| `ViewContainer`  | Required `id`, `name`, `description`, `x`, `y`, `width`, `height`; optional `parentAppearanceId`                                                      | Presentation-only frame, no `entityId`, no graph ports and no authority. Minimum dimensions 240 × 120.                                           |
| New empty frame  | Name `New container`; position 40,40; size 520 × 320; generated ID; explanatory description                                                           | Group-selection frames compute bounds instead. View-item IDs cannot collide with model identities or other view-item identities. Parents must exist in the same view and cannot form cycles. Reparenting/removing a frame preserves world positions; removing a frame retains its children and semantics. Collapsing hides visual descendants. A semantic container renderer, a `contains` edge and a visual frame are three separate features.

#### Assemblies and instances

`AssemblyDefinition` is versioned and has `id`, `version`, `name`, `description`, `entities`, `relationships`, `dependencies`, `parameters` and exposed `ports`. Parameters have `{ name, entityId, property, default }`; exposed ports have `{ name, entityId, portId }`. A selection-built assembly defaults version to `1.0.0`, includes internal edges and direct type/relationship dependencies, and starts with no parameters or exposed ports.

`AssemblyInstance` stores `id`, exact `definitionRef`, `definitionHash`, entity `mapping`, `relationshipMapping`, and parameter values. Insertion allocates fresh graph identities. Upgrades compare old definition, new definition and local values, retain local overrides, and require explicit conflict choices. Exposed ports are mappings to existing ports, not executable interfaces. Recommended hardening: validate all parameter/exposed-port targets, mapped pointers and transitive definition dependencies as explicit schema contracts.

#### Artifacts and reconciliation

`ArtifactBinding` has `id`, `resource: { rootId, path }`, `entityIds`, explicitly chosen `ownership: independent / generated / managed`, `mappings`, optional `baseline`, and `state: unreviewed / accepted / pending / missing`. Each `ArtifactMapping` identifies `id`, `entityId`, `pointer`, `format: markdown / json / text`, and `locator`. A `Baseline` records model revision, resource hash, mapping version, content and accepted mapped values.

These records associate a specification with a file; an `artifact-contract` component alone does not create a binding. Paths are root-relative and checked by the host. Hash-preconditioned, recoverable staged writes remain mandatory. Accepting a model proposal, saving text and accepting reconciliation are separate actions. Ownership overlap/freshness checks, export traceability and read-only Git inspection should retain their own contracts.

Current engine derives error/warning from mandatory/advisory; no per-rule severity configuration. |

#### Project, packages, extensions and proposals

The current `Project` envelope requires `schemaVersion: '1.0.0'`, `id`, `name`, `purpose`, nonnegative safe-integer `revision`, and maps `entities`, `relationships`, `types`, `relationTypes`, `assemblies`, `instances`, `bindings`, `dispositions`, plus arrays `decisions`, `reviews` and object `extensions`. `createProject()` initializes these empty except the built-in definitions, names the project `Untitled system`, and sets revision 0 and purpose `''`.

`DefinitionPackage` requires `format: 'lattice-package@1'`, `name`, `types`, `relations`, `assemblies`, and content `hashes`. Import verifies hashes/dependencies. Export profiles are `portable-spec@1.0.0` and `codex-workspace@1.0.0`. They export semantic definitions; views and local appearance preferences are separate.

Current export also consumes otherwise undeclared `instructions` / `instructionScope` properties on any entity and `supportingFiles` on skills. Instruction scope defaults to the repository root; skill slug derives from explicit slug or name. These fields need formal property schemas because they affect generated files. An extension object can preserve namespaced optional data, but preservation does not make it an executed contract or a portable feature understood by another client.

AI changes are simulated proposals with explicitly scoped data, assumptions and revision-aware command groups. They are not live-provider executions. They cannot record human approval or claim implemented/verified status on their own. Runtime execution, credential storage, file-write permission and application Git operations must not be inferred from the graph vocabulary.

### 9. Recommended schema evolution

This is a proposed design direction, not an approved migration or implementation plan. Prefer extending the existing declarative model over introducing executable component classes or parallel graph stores.

| Proposed record / field            | Minimum specification                                                                                                            | Default and compatibility policy                                                                                                                                                                                      |
| ---------------------------------- | -------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `FamilyDefinition`                 | `id`, `version`, `name`, `description`, `defaultViews`, presentation token ref, display order                                    | First catalog describes the existing six families. No permission or impact behavior inherited from category.                                                                                                     |

| Relationship definition extensions | `description`, optional exact `categoryRef`, optional `sourceTypes` / `targetTypes`, port policy, self-link and duplicate policy | Missing type filters retain current family-only matching. Connection side/order belongs in view/presentation metadata.                                                                                              |
| Presentation profile               | Separate versioned node/edge/family/category tokens: color, border, shape, icon, label, routing and port display                 | Local theme settings override visual tokens only. Add per-view overrides separately from shared semantics. No raw executable renderer code.                                                                           |
| Rule metadata                      | Stable rule ID/version, description, optional severity/mandatory policy and bounded parameters                                   | Existing rule evaluation stays unchanged until explicit new support is added. Enforce valid bounds and allowed placement.                                                                                             |
| Evidence definition                | Immutable check result and artifact/hash references                                                                              | Missing evidence remains unknown; do not synthesize verification.                                                                                                                                                     |

**Property-contract recommendation:** use one documented schema subset and reference resolver throughout registration, import, validation, proposal preview and export. Required means required by validation, not automatically inserted. Additional properties may remain open for exploratory definitions, while stricter implementation profiles explicitly close their contracts. Avoid hard-coded special cases based on slugs for new definitions; bind semantics to explicit registered metadata and bounded rules instead.

**Appearance precedence recommendation:** built-in visual tokens → family/category tokens → type presentation profile → project/view override → local theme adjustment → transient selection/finding overlay. This is a proposed precedence order; current styling is implemented through projection functions and CSS rather than this resolver. Shared semantic changes must never be triggered merely by selection, theme or layout.

**Migration recommendation:** preserve old definitions/pins; introduce new versioned definitions and explicit record migrations; preview property, endpoint, port and finding changes before acceptance; revalidate dependent assemblies and contracts; maintain unknown records without dropping data. Adding new canonical registries requires a deliberately supported project-format version and package/export changes. Do not add new registries under `schemaVersion: '1.0.0'` and claim older clients understand them.

### 10. Review findings and priorities

These are specification-completeness findings from source review, not security vulnerability claims.

| Priority | Finding                                                                                                                                    | Practical implication / recommended resolution                                                                                                                  |
| -------- | ------------------------------------------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| High     | Typed ports compare strings without resolving contract identity or payload schemas.                                                        | Identical missing refs can pass. Add contract resolution, explicit unresolved findings and separate payload contracts.                                          |
| High     | Endpoint restrictions mostly allow every family; the two exceptions still use broad families.                                              | A role can be fulfilled by the wrong structure type; tool use can point to a non-tool capability. Add exact endpoint filters in new relationship versions.      |
| High     | `actorId`, `resourceId`, `maxIterations`, grant action/inheritance and export fields are consumed outside their built-in property schemas. | Schema-valid data can be semantically incomplete, and the Inspector does not expose those undeclared fields as normal schema fields. Declare and document them. |
| Medium   | Default insertion differs by creation path and value-state keys differ by edit path.                                                       | Same definition can yield different initial records. Centralize defaults and normalize status pointers.                                                         |
| Medium   | Family/category metadata and semantic-kind special cases are scattered across source modules.                                              | New custom definitions cannot declare equivalent presentation/semantics reliably. Add metadata registries and explicit rule references only where needed.       |
| Medium   | No generic self-link, duplicate, containment-cycle or per-port cardinality policy.                                                         | Structurally valid graphs can express inconsistent intended designs. Add explicit policies, retaining intentional loops and shared membership.                  |
| Medium   | Loop positive bound accepts any positive number; count bounds can contradict one another.                                                  | Checks can pass unsuitable iteration values or define impossible ranges. Require positive integers for iteration limits and `min <= max`.                       |
| Medium   | `contains`, `systemIds`, assembly mapping and appearance parents are independent.                                                          | Navigation, ownership and visual membership can disagree. Document the distinction and offer explicit synchronization, never inference of authority.            |
| Medium   | Evidence is nonempty-reference checking; human-readable flow conditions are not executed.                                                  | A complete specification is not proof of runtime correctness. Add result evidence separately and keep execution outside model validation.                       |
| Low      | Built-in descriptions are generic and association is directed despite its name.                                                            | Improve descriptions; consider a separately versioned undirected association definition.                                                                        |

Recommended first increment: formalize the already consumed properties, make defaults consistent, and strengthen port/endpoint contracts. Keep family/category customization and richer presentation profiles as separate evolutions so visual settings cannot accidentally change validation or permission meaning.
